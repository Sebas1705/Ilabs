> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Run independent tasks in parallel** (see "Execution order"): each parallel implementer works in its own git worktree and must FIRST verify that its base is the commit named in its dispatch (worktrees are not always cut from the current branch tip: `git merge-base --is-ancestor <sha> HEAD`, else `git merge --ff-only <full sha>`), and its commits are cherry-picked onto the branch after review.

**Goal:** Ship the sixth iLabs module, `guardrails` (find and reversibly redact personal data and secrets, score prompt-injection signals, apply a declarative block/redact/flag policy around a provider call, detect a leaked canary, measure the detectors), in Kotlin and TypeScript, pinned by shared fixtures and shown in a web page and an Android screen.

**Architecture:** `contracts/guardrails/` holds the contract (scanner grammars, the injection phrase table, the pinned constants) and the fixtures. Each language implements `detectPii`, `redact`, `restore`, `detectInjection`, `parsePolicy`, `checkText`, `guardedComplete`, `GuardedProvider`, `withCanary`, `detectionMetrics` and a `runFixture` harness on top of `providers` (`Provider`, `MockProvider`, errors) and `rag` (one additive function, `tokenizeSpans`). Contract tests run every fixture. Demos use the live implementations with the fixtures as samples.

**Tech Stack:** as the previous modules: Kotlin Multiplatform (Android + JVM), TypeScript (pnpm workspace, Vitest), Vite + React, Compose + Material 3, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-15-guardrails-design.md` (binding). Read the sibling modules for conventions (modules/rag and modules/evals in `ts` and `kotlin`, `contracts/rag/README.md` as the model of a finished contract, the `contract` harness pattern in both languages, the shared web fixture loader, the Rag page/screen as the newest demo pattern): fixture runner pattern, aggregated Kotlin contract failures, `invalid fixture:` errors with the same messages in both harnesses, test guard `>= <real fixture count>`, unknown fixture keys rejected on the raw JSON, strict JSON parsing of fixture files in Kotlin, harness typing rules (a wrong JSON type in a fixture is a malformed fixture; a JSON `null` option is a bad value).

**Base:** `main` at the rag squash commit (branch `feat/guardrails`: the design commit plus this plan); the dispatch of every task names the exact base commit.

## Review Focus

1. Scanner strategy: candidates start only where the previous code point is not an ASCII letter or digit; maximal run validated as a whole with no backtracking (`612 345 678 90` is not a phone); the next code point is not an ASCII letter or digit; checksums (Luhn, IBAN mod 97, DNI/NIE mod 23) decide validity; only valid candidates enter overlap resolution (earliest start, then longest, then kind order); `kinds` restricts scanning and resolution; look-alikes do not match (version numbers, dates, order ids, 16 digits failing Luhn) (Tasks 1/2/3).
2. Placeholders: numbering per kind in order of first appearance, reuse for the same kind and text, a shared mapping extended across texts, `restore` in one left-to-right pass without re-scanning, unknown placeholders untouched, placeholder-shaped text in the input not special-cased (Tasks 1/2/3).
3. Injection matching: token anchors through `tokenizeSpans` (folded tokens, code-point spans), leftmost first anchor from which the rest matches, earliest token within `maxGap` for each next anchor, each entry once, signals in table order, integer score capped at 100, delimiters on the raw text (`system:` only at a line start), both languages of the table, near misses (gap of `maxGap + 1`) (Tasks 1/2/3).
4. Check evaluation: every check sees the ORIGINAL text, no short circuit, spans always in the original, the redacted text is one `redact` over the resolved union of the firing redact checks, `block` beats everything in the verdict, `flag` never changes text (Tasks 1/2/3).
5. Guarded call: every non-system message checked (assistant turns too) with one shared mapping and no short circuit across messages; zero provider calls when the input blocks or when a classifier check has no classifier; exactly one call otherwise with the redacted messages and untouched system messages; output checks on the raw reply; output redaction with NEW placeholders that never reuse input ones; only input placeholders restored; provider errors propagate unchanged; `GuardedProvider` returns the blocked text (Tasks 1/2/3).

Also pinned by unit tests in Tasks 2/3: `parsePolicy` rejects every invalid shape with the `invalid policy:` prefix (unknown kind/action/key, `redact` on non-PII, `canary` in input, bad thresholds, empty terms, `null` options); inputs are not mutated; cancellation and non-provider exceptions propagate; `rag`'s `tokenize` equals the projection of `tokenizeSpans` on every `rag` `tokens-*` fixture.

## Contract reference (used by Tasks 1-6)

The binding rules are the "Rules" section of the spec. Fixtures live in `contracts/guardrails/<name>.json` as `{ "name", "setup": { "kind": ..., ... }, "expect": { ... } }`; `name` equals the file name. Spans are `{ start, end }` code-point offsets. Kinds:

- `pii`: `{ text, kinds? }` -> `{ findings: [{ kind, start, end, text }] }`.
- `redact`: `{ text, kinds?, mapping? }` -> `{ text, mapping }` (`mapping` as an ordered list of `[placeholder, original]` pairs); `restore`: `{ text, mapping }` -> `{ text }`.
- `injection`: `{ text }` -> `{ score, signals: [{ id, category, start, end }] }`.
- `check`: `{ text, checks, mapping?, classifier?: { script } }` -> `{ verdict, text, mapping, findings: [{ check, kind, action, fired, details }] }` (`details` per kind: PII findings, injection `{ score, signals }`, deny `{ matches: [{ term, start, end }] }`, length `{ length }`, canary `{ found }`, classifier `{ flagged, label? }`).
- `policy`: `{ policy }` -> `{ error: { kind: "invalid_policy" } }` (or `{ valid: true }` for the few accepting cases).
- `guarded`: `{ request: { messages }, policy, provider: { script }, classifier?: { script }, blockedText? }` -> `{ status, text?, sent?, input, output?, calls, mapping, outputMapping }` or `{ error: { kind } }` (a provider kind or `no_classifier`), with `calls` always present; the harness asserts the provider request is exactly `{ messages: sent }`.
- `canary`: `{ messages, canary }` -> `{ messages }` (the `withCanary` output, exact).
- `metrics`: `{ expected, found }` -> `{ precision, recall, f1, byKind: [{ kind, precision, recall, f1, expected, found, correct }] }`.
- `eval`: `{ samples: [{ text, expected: [{ kind, start, end }] }] }` -> `{ pii: metrics, injection: metrics }` computed by running `detectPii` and `detectInjection` on every sample (the demo's Measure section).
- `table`: `{}` -> every pinned constant (phrase table, secret prefixes, DNI letters, placeholder names, canary sentence parts, blocked text, metric kind order), compared exactly with the constants each library exports.

A classifier script is a list of `{ flagged, label? }` answers consumed in call order (over-calling is a malformed fixture). Harness rules (both languages): guard `fixtures.length >= <real count>`; aggregated failures in Kotlin; unknown keys rejected on the raw JSON; every key an expectation lists is compared and absent optionals must be absent; identical `invalid fixture:` messages in both harnesses.
