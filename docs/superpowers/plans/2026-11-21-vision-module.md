# `vision` Module Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Run independent tasks in parallel** (see "Execution order"): each parallel implementer works in its own git worktree and must FIRST verify that its base is the commit named in its dispatch (worktrees are not always cut from the current branch tip: `git merge-base --is-ancestor <sha> HEAD`, else `git merge --ff-only <full sha>`), and its commits are cherry-picked onto the branch after review.

**Goal:** Ship the seventh iLabs module, `vision` (preprocess an RGB image for a model, read classifier and detector outputs, map boxes back, measure results), in Kotlin and TypeScript, pinned by shared fixtures, with real small models running in a web page and an Android screen.

**Architecture:** `contracts/vision/` holds the contract and the fixtures. Each language implements `resize`, `preprocessGeometry`, `toTensor`, `postprocessClassification`, `postprocessDetections`, `nms`, `iou`, `topKAccuracy`, `averagePrecision`, `meanAveragePrecision`, `classify`, `detect`, `parseModelSpec`, `scriptedModel` and a `runFixture` harness. The model sits behind `VisionModel`; the demos plug real models in (LiteRT on Android, ONNX Runtime Web in the browser) and fall back to a scripted backend built from recorded real outputs.

**Tech Stack:** as the previous modules: Kotlin Multiplatform (Android + JVM), TypeScript (pnpm workspace, Vitest), Vite + React, Compose + Material 3, GitHub Actions; plus LiteRT (Android demo) and ONNX Runtime Web (web demo) as demo-only dependencies.

**Spec:** `docs/superpowers/specs/2026-11-21-vision-design.md` (binding, including the section "Rulings after the builder check"). Read the sibling modules for conventions (modules/rag and modules/guardrails in `ts` and `kotlin`, `contracts/guardrails/README.md` as the model of a finished contract, the `contract` harness pattern in both languages, the shared web fixture loader, the Guardrails page/screen as the newest demo pattern): fixture runner pattern, aggregated Kotlin contract failures, identical `invalid fixture:` messages in both harnesses, test guard `>= <real fixture count>`, unknown keys rejected on the raw JSON, strict JSON parsing of fixture files in Kotlin, harness typing rules (a wrong JSON type in a fixture is a malformed fixture; JSON `null` for an option is a bad value), no-regex and code-based rules.

**Base:** `main` at the guardrails squash commit (branch `feat/vision`: the design commit plus this plan); the dispatch of every task names the exact base commit.

## Global Constraints

- Public repo `Sebas1705/ilabs`, MIT; no secrets, no local paths or usernames in tracked files (plans, reports and docs included). Commits conventional, no trailers (no Co-Authored-By, no "Generated with"); do NOT push; push/PR/tag only when the owner asks.
- Repo content in English; demo UI texts in es + en (identical key sets; Android keys prefixed `vision_`).
- Same results in Kotlin and TS = deterministic logic only. Resize, geometry, normalization, softmax, decoding, NMS, IoU and metrics are in the contract; real model inference, image file decoding (JPEG/PNG/EXIF) and clocks are not.
- Kotlin targets Android + JVM only; Gradle project `:modules:vision-kotlin` (dir `modules/vision/kotlin`), package `es.sebas1705.ilabs.vision` (harness in `es.sebas1705.ilabs.vision.contract`); TS package `@ilabs/vision` (dir `modules/vision/ts`). The library has NO dependency on `providers` or any model runtime; the runtimes (LiteRT, ONNX Runtime Web) are dependencies of the demos only.
- Arithmetic: IEEE doubles with the operation order written in the contract; only `+ - * /`, `floor` and comparisons in resize, geometry, normalization, IoU, NMS and metrics (bit-identical in both languages; no FMA, no `Math.fround`, no float32 in the library); `exp` (softmax) and the logistic function may differ in the last bits between platforms: compared with absolute tolerance `1e-9`, ranks and tie orders exact; no fixture contains different scores closer than `1e-9`. Rounding is `floor(v + 0.5)` everywhere (never `Math.round`, `roundToInt`, `rint`).
- No Unicode- or locale-aware helpers for any contract rule; labels are opaque strings; no regular expressions in library code.
- Model files are NEVER committed and CI never needs them: the demos load real models only when the files are present (git-ignored folder filled by a checksum-verifying download script) and otherwise stay on the scripted backend. Sample images and recorded outputs are small, license-free and listed with their licenses.
- Demos work offline once the models are downloaded (or without them on the scripted backend); no keys.
- Tooling: pnpm via `corepack pnpm`; Kotlin builds need JDK 21 (`JAVA_HOME`) and the Android SDK (`ANDROID_HOME` or `local.properties`); the dispatch gives the machine paths.
- CI aggregates Kotlin module tests through `./gradlew jvmContractTests` (picks `:modules:*-kotlin` automatically); do not edit CI per module.

## Review Focus

1. Resize: destination-to-source mapping `sx = (x + 0.5) * srcW / dstW - 0.5` in the written operation order, nearest `floor(sx + 0.5)` clamped, bilinear weights and the clamped neighbours, `floor(v + 0.5)` rounding and clamp to `[0, 255]`, 1x1 and extreme ratios, byte-exact fixtures (Tasks 1/2/3).
2. Geometry and unmapping: `stretch`, `centerCrop` (`scaledW = max(dstW, round-half-up(srcW * scale))`, whole image resized then cut, `offsetX = -cropX`), `letterbox` (uniform `scale`, `newW = max(1, ...)`, `scaleX = newW/srcW`, centered integer padding), `unmapBox` through every mode, clamping, zero-area boxes dropped, a box entirely inside the padding (Tasks 1/2/3).
3. Tensor: channel swap before normalization, `mean`/`std` indexed by OUTPUT channel, `padValue` normalized like pixels, `uint8` keeps swap and layout but no scale/mean/std, `nhwc` vs `nchw` ordering (Tasks 1/2/3).
4. Outputs: stable softmax, top-k ties by ascending index, `minScore`, labels and `labelOffset`, the `ssd` decoder (batch squeeze, `boxOrder`, `coordinates`, `count` truncating `n`), the `rows` decoder (`transposed`, `objectness`, `boxFormat`, `scoreActivation`), the detection order (best class, threshold `>=`, coordinate swap, NMS, sort, cut, unmap, drop), class-aware NMS with the strict `>` IoU boundary and ties by original index (Tasks 1/2/3).
5. Metrics and pipeline: VOC-style AP (best truth only, no fallback, envelope, empty cases), `meanAveragePrecision` over classes with truths (0 with none), `topKAccuracy` empty set 0 and `k >= 1`, the pipeline's single model call, the recorded input tensor, the four clock calls and the three timings, model errors propagating unchanged, `invalid_output` for malformed outputs before any result (Tasks 1/2/3).

Also pinned by unit tests in Tasks 2/3: `parseModelSpec` rejects every invalid shape with the `invalid model spec:` prefix; inputs never mutated; huge images do not overflow (Kotlin `Int` arithmetic: sizes above 16,384 per side are out of scope and rejected with `invalid_options`); a non-provider exception or `CancellationException` from the model propagates; resize of a 4096x4096 image completes in a few seconds with linear cost.

## Contract reference (used by Tasks 1-7)

The binding rules are the spec's "Rules" and "Rulings after the builder check". Fixtures live in `contracts/vision/<name>.json` as `{ "name", "setup": { "kind": ..., ... }, "expect": { ... } }`; `name` equals the file name. Images in fixtures are `{ "width", "height", "data": [bytes] }` (flat RGB array, kept tiny: at most 8x8). Kinds (the contract author pins every key):

- `resize`: `{ image, width, height, method }` -> `{ image }`.
- `geometry`: `{ srcWidth, srcHeight, spec, boxes?: [{x1,y1,x2,y2}] }` -> `{ geometry: { scaleX, scaleY, offsetX, offsetY, newWidth, newHeight }, unmapped?: [...] }`.
- `tensor`: `{ image, spec }` -> `{ shape, data }` (tolerance `1e-9`).
- `classify`: `{ output: [numbers], spec, options? }` -> `{ entries: [{ index, label, score }] }`.
- `decode`: `{ outputs: { name: tensor }, spec, geometry or srcWidth/srcHeight, options? }` -> `{ detections: [{ box, classIndex, label, score }] }`.
- `nms`: `{ detections, iouThreshold }` -> `{ detections }`.
- `metrics`: `{ op: "iou"|"topk"|"ap"|"map", ... }` -> values (tolerance `1e-9`).
- `pipeline`: `{ image, spec, task: "classify"|"detect", scripted: { outputs }, options?, clock?: [4 numbers] }` -> `{ results, timing, modelCalls: 1, clockReads: 4, input: { shape, data } }`.
- `spec`: `{ spec }` -> `{ error: { kind: "invalid_spec" } }` or `{ valid: true }`.
- Any kind may expect `{ "error": { "kind" } }` (`invalid_options`, `invalid_output`, `invalid_spec`): there is no separate `invalid` kind; `contracts/vision/README.md` is the authority for every key and rule.

Harness rules (both languages): guard `fixtures.length >= <real count>`; aggregated failures in Kotlin; unknown keys rejected on the raw JSON; every key an expectation lists is compared and absent optionals must be absent; identical `invalid fixture:` messages in both harnesses; byte arrays compared exactly, doubles with tolerance `1e-9` and ranks exactly.
