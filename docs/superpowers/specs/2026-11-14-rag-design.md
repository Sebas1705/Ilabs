# `rag` module — design

Status: draft for owner approval · Date: 2026-11-14 · Parent: [2026-11-11-ilabs-design.md](2026-11-11-ilabs-design.md)

## Intent

Give a model the right passages of a small corpus, deterministically and measurably. `rag` splits documents into chunks, indexes them, retrieves the best chunks for a question with three methods (lexical BM25, dense vectors, and their fusion), composes a numbered-sources context, checks the citations in an answer, and scores retrieval against labelled questions. It is the fifth iLabs module: it plugs into `providers` (the answer call), `context` (the token budget of the composed context) and `evals` (answers and retrievals can be graded with the existing suites).

The owner built it for the portfolio and to practise the technique for interviews. So the module is a readable, honest tour of the standard pieces (chunking, sparse vs dense retrieval, hybrid fusion, grounding, retrieval metrics) and says plainly where it is a teaching-scale stand-in for production tooling.

## Goals / non-goals

- Same behavior in Kotlin (KMP) and TypeScript, pinned by shared fixtures in `contracts/rag/`, like the previous modules.
- Deterministic only: chunking, tokenization, BM25, the built-in hashed embedder, cosine similarity, reciprocal-rank fusion, ranking and tie-breaking, context composition, citation extraction and the retrieval metrics are in the contract. A real embedding model, a real model answer and the wording of the instruction to the model are NOT.
- Goal: a pluggable `Embedder` so a real model (an API through `providers`, or an on-device model later) can replace the built-in one without touching the contract.
- Non-goals: persistence and SQLite (the index is in memory; storage is a later iteration), approximate nearest neighbour (search is brute force), a trained embedding model, rerankers, query rewriting, stemming, NFC normalization and case or accent folding beyond the pinned Latin-1 table (documented limits), streaming, multimodal content.
- Anti-goal: presenting the hashed embedder as semantic search. It matches character n-grams, not meaning; the README and the demo say so.

## Approaches considered

- **A. Lexical only** (chunker + BM25 + context + metrics): small and fully deterministic, but there are no embeddings, which is the most common interview topic.
- **B. Lexical + dense + hybrid, with a pluggable `Embedder` and a deterministic built-in one (chosen by the owner):** everything, including the dense side, is pinned by fixtures; real embedders plug into the interface; covers chunking, sparse vs dense, fusion, grounding and evaluation. Cost: the built-in embedder is weaker than a real one.
- **C. B plus real embeddings and SQLite storage:** the most impressive, but not deterministic, much heavier and needs keys or a local model. Later iteration; the contract stays as it is.

## Rules (my calls, to confirm)

**Corpus and chunks.** A document is `{ id, text }` (ids non-empty and unique, text any string). `chunkDocument(doc, options)` returns chunks `{ id, docId, index, text, start, end }` where `start`/`end` are code-point offsets into the document text and `id = docId + "#" + index` (index from 0). Lone surrogates count as one code point, as in the other modules. Two strategies, pinned exactly:
- `fixed { size, overlap }`: windows of `size` code points advancing by `size - overlap`; the last window ends at the end of the text (it may be shorter; no window is emitted whose span is entirely contained in the previous one). `size >= 1`, `0 <= overlap < size`.
- `paragraph { maxSize }`: a *line break* is LF or CRLF (a lone CR is an ordinary character). A paragraph separator is a run of two or more line breaks; line breaks at the very start or end of the text are separators too. Paragraphs are the maximal spans between separators (the span excludes the separator); a paragraph made only of ASCII whitespace (space, tab, CR, LF) is dropped. Consecutive paragraphs are packed greedily into one chunk, the chunk text being the ORIGINAL slice from the first paragraph's start to the last paragraph's end (separators included, so a CRLF separator costs more than an LF one), as long as that slice has `<= maxSize` code points. A paragraph longer than `maxSize` first flushes the current pack, is cut with `fixed { size: maxSize, overlap: 0 }`, and each piece is its own chunk (pieces are never packed with later paragraphs). `maxSize >= 1`.
- An empty document yields no chunks; empty `text` is valid.

**Tokenization (BM25 and the built-in embedder).** A token is a maximal run of *word code points*; every other code point separates tokens. Word code points are ASCII letters and digits and any code point `>= 0x80` that is not a separator. Pinned separators beyond ASCII (so Spanish and English punctuation does not stick to words): U+00A0 to U+00BF (NBSP, `¡`, `«`, `»`, `¿`, `·`, ...), U+00D7 `×`, U+00F7 `÷`, and U+2000 to U+206F (General Punctuation: spaces, dashes, curly quotes, ellipsis, ...). Folding, applied code point by code point, in this order: ASCII `A-Z` to `a-z`; then a pinned table for the Latin-1 letters (upper AND lower case of every group: `À Á Â Ã Ä Å` → `a`, `Ç` → `c`, `È É Ê Ë` → `e`, `Ì Í Î Ï` → `i`, `Ñ` → `n`, `Ò Ó Ô Õ Ö Ø` → `o`, `Ù Ú Û Ü` → `u`, `Ý ÿ` → `y`, `Æ` → `ae`, `ß` → `ss`, `Ð` → `d`, `Þ` → `th`; that is the 62 letters of U+00C0 to U+00FF without `×` and `÷`); every other code point is kept as is (no NFC/NFD normalization, no stemming, no Latin Extended or non-Latin case folding: documented limits). The table lives in `contracts/rag/README.md` and is copied verbatim into both implementations. Token position is not used. Lone surrogates are word code points. Chunks with no tokens are indexed but never retrieved by BM25.

**BM25.** For a query token `q` with document frequency `n(q)` over `N` chunks: `idf = ln(1 + (N - n + 0.5) / (n + 0.5))`; `score(chunk) = sum over distinct query tokens of idf * tf*(k1+1) / (tf + k1*(1 - b + b*len/avgLen))`, `k1 = 1.2`, `b = 0.75`, `len` = token count of the chunk, `avgLen` = mean over all chunks. A query token repeated in the query counts once. Chunks scoring 0 are not hits.

**Built-in embedder (`hashEmbedder`).** `dim` default 256 (`>= 1`). For each token (as above, after the same folding), take `w = "<" + token + ">"` and every window of 3 code points of `w` (a one-code-point token gives `w` of exactly 3 code points: its single window, counted once; the whole token is NOT added on top of the windows). Each window occurrence adds to the vector (so repeats count, like term frequency): hash the window's UTF-8 bytes with FNV-1a 32-bit (unsigned), bucket `h % dim`, sign `+1` if bit 31 of `h` is 0 else `-1`. UTF-8 is encoded by hand in both languages and a lone surrogate encodes as U+FFFD (`EF BF BD`), so the twins agree. L2-normalize (a zero vector stays zero). Text with no tokens embeds to the zero vector. Integer arithmetic is exact in both languages; floats are summed in dimension order and compared in fixtures with an absolute tolerance of `1e-9`.

**Dense retrieval.** The index stores one embedding per chunk (`Embedder.embed(texts)`, async, returns vectors of equal length). Query embedding is the same call. Score = dot product (the vectors are normalized, so this is the cosine); chunks with score `<= 0` are not hits.

**Hybrid.** Reciprocal-rank fusion over the BM25 ranking and the dense ranking (each cut at `candidates`, default 50): `score = sum 1 / (60 + rank)` with rank 1-based; a chunk present in one list gets only that term. `k = 60` is fixed.

**Ranking and ties.** Hits are ordered by descending score; only EXACTLY equal scores tie (no tolerance, so the order is a total order and sorting is safe), and ties are broken by ascending chunk order in the index (document order then chunk index); `rank` is the 1-based position after that order; `topK >= 1` default 5. Each hit carries `{ chunkId, docId, rank, score }` plus, in hybrid, `bm25Rank?` and `denseRank?` (absent when the chunk was not in that list). Scores are compared in fixtures with the `1e-9` tolerance, ranks exactly; fixtures must not contain scores that are different but closer than `1e-9` (they could order differently in the two languages); ties by exact construction are fine.

**API.** `buildIndex(documents, { chunking, embedder? })` (async; without an embedder the dense and hybrid modes fail with `RagError(no_embedder)`); `search(index, query, { mode: "bm25" | "dense" | "hybrid", topK?, candidates? })`; `composeContext(hits, index, { maxTokens, counter? })`; `extractCitations(answer, sources)`; `retrievalMetrics(hits, relevant, { level? })`; `answerWithSources(provider, index, query, options)`. Option rules (each has an `invalid` fixture with `expect.error = {kind}`): documents have non-empty unique ids (`invalid_options`); `size`, `maxSize`, `topK`, `maxTokens`, `dim`, `candidates` are integers `>= 1` (`overlap` an integer with `0 <= overlap < size`); `candidates` is only used and validated by `hybrid` (ignored by the other modes), where it must be `>= topK` when given; absent means 50 and is never compared with `topK`; an unknown `mode` or `level` is invalid; a JSON number that is not an integer (`2.5`) where an integer is required is invalid in both languages; an embedder returning the wrong number of vectors or vectors of different lengths fails with `invalid_embedding`; `no_embedder` as above. Errors are `RagError(kind)` (a TS class / Kotlin exception) so fixtures can name the kind; typed APIs may also use `RangeError`/`IllegalArgumentException` for programmer errors that fixtures cannot express. `search` of a query with no tokens returns no hits.

**Context composition.** `composeContext(hits, index, { maxTokens, counter? })` walks the hits in array order (which is rank order for `search` results) and keeps each chunk as a *source* while the composed system message fits the budget (token cost from `context`'s default counter, `4 + ceil(codePoints/4)`, on the whole composed message); the first chunk that does not fit stops the walk (no skipping, like the sliding window). The budget covers the composed system message only: the user message with the query is not charged (the caller chooses `maxTokens` knowing that). The composed message is ONE `system` message whose content is PINNED exactly: the constant `RAG_INSTRUCTION` (defined in `contracts/rag/README.md` and copied verbatim into both implementations: "Answer the question using only the numbered sources below. Cite the sources you use as [n]. If the sources do not contain the answer, say so."), then a blank line (`\n\n`), then the sources block: `[n] <chunk text>` entries separated by one blank line (`\n\n`), `n` starting at 1 in that order, no trailing newline. Result `{ message, sources: [{ n, chunkId, docId }], droppedCount }`; if not even the first source fits, `RagError(budget_too_small)` with `required` (the cost of the message with the first source). Empty hits give the instruction alone, no sources and `droppedCount 0`, provided the instruction itself fits the budget (otherwise `RagError(budget_too_small)`; `answerWithSources` then makes no provider call).

**Citations.** `extractCitations(answer, sources)` finds markers `[n]` where `n` is 1 to 9 ASCII digits without leading zeros and `>= 1`, in order of first appearance, deduplicated. `cited` lists the markers whose `n` is in `sources`; `unknown` lists the others; the two lists are disjoint. A marker is exactly `[`, those digits, `]`: `[1,2]`, `[ 1 ]`, `[01]` and numbers of ten or more digits are not markers. Digit tests are on ASCII `0-9` only (no Unicode digits).

**Retrieval metrics.** `retrievalMetrics(hits, relevant, { level })`, `level` `"chunk"` (default) or `"doc"`; `relevant` is a non-empty set of chunk ids (or doc ids). At `"doc"` level the hits are first deduplicated by document keeping the best-ranked hit of each, and everything is computed on that list. Then `recallAtK = (distinct relevant found) / |relevant|`, `precisionAtK = (relevant hits) / (number of hits)` (0 with no hits), `reciprocalRank = 1 / rank of the first relevant hit in that list` (0 when none), `hit = any relevant`. An empty `relevant` set is invalid (`invalid_options`). Floats are IEEE doubles computed in the same order in both languages and compared exactly.

**`answerWithSources(provider, index, query, { mode, topK, maxTokens, ... })`.** Search, compose, then ONE provider call: the request is the composed `system` message plus a `user` message with the query; provider errors propagate unchanged. Result `{ answer: reply.text, sources, citations, hits }`. No retries.

**Fixtures.** `contracts/rag/<name>.json`, one `setup.kind` per area: `chunk` (documents, strategy, options → chunks), `bm25` / `dense` / `hybrid` (documents, chunking, query, topK → hits with ranks and scores), `context` (hits or a query, maxTokens → message text, sources, droppedCount or `budget_too_small`), `citations`, `metrics`, `eval` (documents, chunking, labelled questions `{query, relevant}` and `topK` → the metrics per mode per question; the demo's labelled questions come from here), `answer` (a scripted provider reply and the expected sources/citations; the request is the pinned composed system message plus a user message with the query), plus `invalid` (every option rule → `expect.error = {kind}`, zero provider calls). About 70 fixtures: chunk edges (empty, shorter than size, exact multiple, overlap, paragraph packing, oversized paragraph, CRLF, emoji/surrogates, lone surrogate), tokenization (ASCII fold, the pinned Latin-1 table incl. `ß` and `æ`, digits, `¿¡«»` and General Punctuation as separators, `canción` matching `cancion`, characters outside the table kept as is), BM25 (idf with N=1, repeated query token, zero-score exclusion, length normalization, ties), embedder (one-code-point token, empty text, hash buckets of known words, sign collisions), dense (zero vector, similar spellings ranking above unrelated words), hybrid (rank present in one list, fusion order flips vs each side alone), context (budget exact, first source too big, order), citations, metrics, answer. Harness rules like `evals`: unknown keys rejected in fixture files, guard `>= <count>`, aggregated failures, floats by tolerance. (This paragraph is the original sketch: the authoritative list of setup kinds, the fixtures and their count (144) are in `contracts/rag/README.md`.)

## Demos

A web page and an Android screen using the live implementations over a small bilingual sample corpus (the fixtures' documents). The user picks a corpus (fixture) and a question (typed, or a labelled one from the fixture), a mode (BM25, dense, hybrid) and `topK`; the page shows the chunks with their position in the document, the ranked hits with BM25 score, dense score, fused score and ranks side by side (so the effect of fusion is visible), the composed context with its `[n]` sources and the token budget bar, the citation check of the scripted answer when the fixture has one, and, for labelled questions, recall / precision / MRR for each of the three modes. A short note says the dense side is the built-in n-gram hashing embedder, not a model. es + en, light/dark, same shell as the other modules; one entry in the web route registry and the Android module home.

## Groundwork

None needed: the demos' structure (route registry, shared fixture loader, module home) already scales. One shared helper decision: `rag` depends on `context` only for the token counter and on `providers` for `answerWithSources`; no other coupling.

## Left to the builder

File layout, error type names, the wording of the instruction to the model in the composed message, UI copy, how scores and ranks are laid out, and the sample corpus text (small, bilingual, license-free: written for the repo).
