# `guardrails` module — design

Status: draft for owner approval · Date: 2026-11-15 · Parent: [2026-11-11-ilabs-design.md](2026-11-11-ilabs-design.md)

## Intent

Check what goes into a model and what comes out of it, deterministically and measurably. `guardrails` finds personal data and secrets in text, replaces them with reversible placeholders, scores prompt-injection signals, applies a small declarative policy (block, redact or flag, on the input and on the output), wraps any `Provider` so the checks run around the call, detects a leaked canary, and measures its own detectors against labelled text. It is the sixth iLabs module: it plugs into `providers` (the guarded call), reuses `rag`'s tokenizer (the pinned folding table) and can be graded with `evals`.

The owner wants it for the portfolio and for interviews, with privacy (PII) and attack safety (prompt injection) weighted equally. So the module is a readable tour of where guardrails sit (input vs output, defense in depth, reversible redaction, canaries, measuring precision and recall) and it says plainly that lexical injection signals are a signal, not a defense.

## Goals / non-goals

- Same behavior in Kotlin (KMP) and TypeScript, pinned by shared fixtures in `contracts/guardrails/`, like the previous modules.
- Deterministic only: the PII and secret scanners with their checksums, overlap resolution, placeholders and restoring, the injection phrase table and scoring, policy validation and evaluation order, the guarded call bookkeeping (what is sent, call counts, statuses), the canary check and the detection metrics are in the contract. A real safety classifier or a model judge is NOT (it plugs in through `Classifier`; fixtures script its answers).
- Non-goals: names, addresses and other data that needs a trained recognizer (NER); national identifiers other than the Spanish DNI/NIE; regular expressions (hand-written scanners, as in the other modules); streaming; guarding tool calls; rate limiting; language detection.
- Anti-goal: presenting the injection heuristics or the PII scanners as complete protection. The README and the demos state the false positives and the misses they have.

## Approaches considered

- **A. Detectors only:** pure functions for PII and injection signals. Small, but it does not show where the checks go or what happens when one fires.
- **B. Detectors + policy + guarded provider (chosen by the owner):** everything in the contract, a `Classifier` extension point for real models, reversible redaction, canary, metrics. Cost: larger; the heuristics are honest about being heuristics.
- **C. B plus real classifiers** (local safety models or an API): more realistic, not deterministic, heavy. Later, through `Classifier`.

## Rules (my calls, to confirm)

**Offsets and tokens.** Offsets are code points (a lone surrogate counts one), as everywhere in iLabs. Word-level rules use `rag`'s tokenizer (ASCII lower-casing plus the pinned Latin-1 table), so `Ignóra` and `ignora` are the same token. Because spans are needed, `rag` gains one ADDITIVE public function in both languages, `tokenizeSpans(text)` → `[{ token, start, end }]` (code-point offsets of the source run; `tokenize` becomes a projection of it, with unit tests in `rag`; no change to the `rag` fixtures).

**PII and secret scanners.** `detectPii(text, { kinds? })` returns findings `{ kind, start, end, text }` in order of `start`. Matching strategy, pinned for every kind: a candidate may start only where the previous code point is not an ASCII letter or digit ("glue" is ASCII-only: `aquí612345678` does match because `í` is not ASCII, documented); from a start, each kind consumes its MAXIMAL run (greedy, separators included) and validates that run as a whole (length bounds, shape, checksum); there is no backtracking to a shorter run, so `612 345 678 90` (11 digits) is not a phone; the code point after the run must not be an ASCII letter or digit; only valid candidates take part in overlap resolution. Kinds and their rules (hand-written scans over ASCII):
- `email`: `local@domain`, local part of ASCII letters, digits and `. _ % + -` (no leading or trailing dot), domain of labels of letters, digits and `-` separated by dots, last label at least 2 letters.
- `phone`: `+` followed by 8 to 15 digits, or a Spanish national number of 9 digits starting with 6, 7, 8 or 9; single spaces, dots or hyphens between digit groups are allowed and belong to the match.
- `iban`: 2 uppercase letters, 2 digits and 11 to 30 letters or digits, optionally written in groups separated by single spaces; valid only when the mod-97 check equals 1.
- `card`: 13 to 19 digits, optionally in groups separated by single spaces or hyphens; valid only when the Luhn check passes.
- `spanish_id`: DNI (8 digits and the control letter of the mod-23 table) or NIE (`X`, `Y` or `Z`, 7 digits and the control letter); letters in either case; an optional hyphen before the letter.
- `secret`: a pinned list of key prefixes (`sk-`, `pk-`, `ghp_`, `gho_`, `github_pat_`, `AKIA`, `xoxb-`, `xoxp-`, `AIza`) followed by at least 16 characters of letters, digits, `_` or `-`.
Overlaps: findings never overlap; among valid candidates the earliest start wins, then the longest, then the kind order above (so a card number inside a longer IBAN is the IBAN). With `kinds` given, only those kinds are scanned and resolved (`kinds: ["card"]` can report a Luhn-valid run that sits inside an IBAN).

**Redaction.** `redact(text, findings, mapping?)` replaces each finding with a placeholder `<KIND_n>` (`<EMAIL_1>`, `<PHONE_2>`, …): `n` counts per kind from 1 in order of first appearance; the same original text of the same kind reuses its placeholder; a given `mapping` is extended (numbering continues), so a conversation shares one mapping. It returns `{ text, mapping }` (`mapping`: placeholder → original, in creation order). `restore(text, mapping)` replaces every occurrence of a mapped placeholder in ONE left-to-right pass (restored text is never re-scanned); unknown placeholders are left as they are. Text that already contains something shaped like a placeholder is not special-cased (documented limit).

**Injection signals.** `detectInjection(text)` returns `{ score, signals: [{ id, category, start, end }] }`. The contract pins a bilingual (en + es) phrase table (about 30 entries): each entry has an `id`, a `category` (`override`: ignore/disregard/forget … previous/prior/above … instructions/rules; `role_hijack`: you are now, act as, pretend to be; `prompt_leak`: reveal/show/print/repeat … system prompt/instructions; `delimiter`: fake role markers such as `system:` at the start of a line, `### system`, `<|im_start|>`, `[INST]`), an integer `weight` (1 to 100) and a pattern. A token pattern is a sequence of 2 to 4 anchors, each a set of single-token alternatives, with a per-entry `maxGap` (0 for fixed phrases such as `you are now`, up to 3 otherwise): matching takes the leftmost token matching the first anchor from which the rest can be matched, and for each following anchor the EARLIEST token within the gap; the span runs from the start of the first anchor token to the end of the last. Delimiter entries are literal ASCII strings matched on the raw text (case-sensitive; `system:` only at the start of a line). Each entry counts once (its first match); `score = min(100, sum of the weights of the entries that matched)`, an INTEGER from 0 to 100 (no floating point); `signals` are listed in table order. Negations are not understood (`do not ignore the previous instructions` matches: documented). The table lives in `contracts/guardrails/README.md` and is copied verbatim into both implementations.

**Other checks.** `maxLength { max }` (code points); `denyTerms { terms }` (each term is tokenized; it matches a contiguous token sequence of the text; findings carry the term and span).

**Canary.** The caller supplies a canary string (non-empty, no whitespace). `withCanary(messages, canary)` returns the messages with one pinned sentence carrying the canary appended to the first `system` message (or a new first `system` message when there is none). The guarded call never inserts it by itself: the caller applies `withCanary` and puts a `canary` check in the policy's `output`. A canary check fires when the output contains the canary as a substring.

**Policy.** `{ input: Check[], output: Check[] }`; a check is `{ kind, action, …params }` with `kind` one of `pii { kinds? }`, `injection { threshold }` (fires when `score >= threshold`, an integer from 1 to 100), `denyTerms { terms }` (a non-empty list of terms with at least one token each), `maxLength { max }`, `canary { canary }` (output only), `classifier { label? }`, and `action` one of `block`, `redact` (only for `pii`) or `flag`. `parsePolicy(json)` validates everything and fails with `invalid policy: <reason>` (prefix pinned, as `invalid suite` in `evals`): unknown kinds, actions or keys, `redact` on a non-PII check, `canary` in `input`, bad parameters, JSON `null` for an option.

**Evaluating text.** `checkText(text, checks, { mapping?, classifier? })` runs ALL the checks in order (no short circuit), and EVERY check evaluates the ORIGINAL text (a `redact` check never hides anything from a later check, the classifier receives the original text, and every span in the findings is an offset into the original text). Result `{ verdict: "allow" | "block", text, mapping, findings: [{ check: index, kind, action, fired, details }] }`: `verdict` is `block` when any firing check has `action: "block"`; `text` is the original with the union of the PII findings of every firing `redact` check replaced (the union goes through the same overlap resolution, then one `redact`); `flag` only records.

**Guarded call.** `guardedComplete(provider, request, policy, { classifier? })`:
1. Input: EVERY non-system message (user and assistant turns: history can carry injected text) goes through the input checks in message order, sharing one mapping; all messages are checked even after one blocks (so the findings list has one entry per non-system message and the classifier is called once per classifier check per message, in that order). If any message is blocked the provider is NOT called: `status: "blocked_input"`.
2. Otherwise ONE provider call with the redacted messages (system messages are never checked or changed; provider errors propagate unchanged).
3. Output: the raw reply goes through the output checks (before restoring anything). Blocked → `status: "blocked_output"` (the reply is not returned).
4. Otherwise `status: "ok"`: output redaction replaces its findings with NEW placeholders (numbering continues after the input mapping; an input placeholder is never reused, even for the same value), then the placeholders of the INPUT mapping, and only those, are restored. So data the user sent comes back, and data the model produced on its own stays hidden. `outputMapping` is computed from the output redact checks even when the output is blocked; `sent` and `output` are absent when the input blocks.
Result `{ status, text?, input: findings per non-system message, output: findings, calls: 0 | 1, sent: the messages actually sent, mapping, outputMapping }`. `GuardedProvider(provider, policy, { classifier?, blockedText? })` is the same as a `Provider` (for `rag` and `evals`): a blocked call returns `blockedText` (default pinned: `"Request blocked by guardrails."`) as the reply text; its `lastReport` holds the last result.

**Classifier.** `Classifier = (text) => Promise<{ flagged: boolean, label?: string }>`. A `classifier` check fires when `flagged` is true (and, if the check names a `label`, when the labels are equal). No classifier supplied → the check errors the call with `GuardrailError(no_classifier)` before any provider call. Classifier exceptions propagate.

**Detection metrics.** `detectionMetrics(expected, found)` over spans `{ kind, start, end }` (for injection signals the `kind` is the `category`); both lists are treated as sets (duplicates count once). A found span is correct when an expected span has the same kind, start and end. `precision = correct / found` (1 when nothing was found), `recall = correct / expected` (1 when nothing was expected), `f1 = 2 * correct / (|expected| + |found|)` computed with ONE division (equal to the harmonic mean of precision and recall, without the rounding of the two-step formula; 1 when both sets are empty); exact doubles. The result has the totals and a per-kind breakdown listing only the kinds present in `expected` or `found`, in the pinned order: the six PII kinds, then the four injection categories.

**Errors.** `GuardrailError(kind)` with `invalid_policy` (policy shapes), `invalid_options` (other bad arguments: unknown metric kinds, a bad canary, bad `kinds`) and `no_classifier`; malformed fixtures are `invalid fixture:` as in the other harnesses.

**Fixtures.** `contracts/guardrails/<name>.json`, kinds: `pii` (text → findings), `redact` / `restore`, `injection` (text → score and signals), `check` (text + checks → verdict, text, findings), `policy` (invalid policies → `invalid policy`), `guarded` (request, policy, provider script, optional classifier script → status, text, sent messages, findings, calls), `canary`, `metrics`, a labelled set kind `eval` (texts with expected spans → metrics per detector, used by the demo) and one `table` fixture holding every pinned constant (the phrase table, secret prefixes, DNI letters, placeholder names, canary sentence, blocked text), compared exactly with the constants each library exports. About 150 fixtures: every scanner edge (checksum valid and invalid, separators, glued characters, case, overlaps, look-alikes that must NOT match such as version numbers, order ids, dates), placeholders (numbering, reuse, shared mapping, restore with unknown placeholders), every phrase-table entry in both languages plus near misses (gap of 4 tokens, negations are still matched: documented), policy validation (one violation each), check order and redaction order, guarded statuses and call counts, provider errors, classifier scripted answers, canary leak, metrics arithmetic.

## Demos

A web page and an Android screen using the live implementations with the fixtures as samples. (1) **Playground**: paste or pick a text; the findings are highlighted inline with their kind (text label, not colour alone), the redacted text and its mapping are shown, the injection score with the signals that fired, and the policy verdict for an editable set of check toggles. (2) **Guarded conversation**: pick a sample (fixture) and see the request as written, what was actually sent to the model (redacted), the model reply, the output checks, and the final text with placeholders restored, or the blocked state and why. (3) **Measure**: the labelled set with precision, recall and F1 per detector, and the list of misses and false positives. A note says the injection score is a lexical heuristic. es + en, light/dark, same shell as the other modules.

## Left to the builder

File layout, error type names, the exact phrase table entries beyond the categories above (kept small and justified), the pinned canary sentence wording, UI copy, how highlights and scores are laid out, and the sample texts (written for the repo, with obviously fake data: reserved example domains, test card numbers, generated IBANs).
